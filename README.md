# A/B-эксперимент: планирование и анализ конверсии

**Python · statsmodels · NumPy · SciPy · Matplotlib**

Учебный проект: расчёт необходимой выборки, симуляция двух групп, проверка статистической значимости, оценка влияния на конверсию и сравнение статистического эффекта с практическим порогом.

Все данные в demo/ синтетические. Реальный продуктовый эксперимент не проводился. Результат не выбирается перебором seed.

## Быстрый запуск на Windows

Установите Python 3.11 или 3.12. Распакуйте архив, откройте PowerShell в папке ab-experiment:

```powershell
py -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m abtest demo --out local/my-demo --seed 42
```

Откройте local/my-demo/analysis/REPORT.md. Рядом будут result.json и график effect.png.
Готовый выполненный пример уже находится в demo/analysis/REPORT.md.

Linux/macOS:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
python -m abtest demo --out local/my-demo --seed 42
```

Дальнейшие команды выполняйте в активированном окружении. В Windows можно заменять python на `.\.venv\Scripts\python.exe`.

## Что делает проект

- Планирует сравнение двух независимых долей при равном распределении A/B и двусторонней гипотезе.
- Рассчитывает выборку по Cohen’s h и NormalIndPower из statsmodels.
- Создаёт бинарные пользовательские исходы с фиксированным seed.
- Считает конверсии, абсолютную разницу B−A, относительный uplift и доверительный интервал Newcombe.
- Применяет pooled z-test; при ожидаемых частотах меньше 5 — точный тест Фишера.
- Проверяет sample ratio mismatch (SRM) при ожидаемом распределении 50:50.
- Показывает, набрана ли минимальная плановая выборка, и блокирует итоговое решение при её нехватке или SRM.
- С помощью Monte Carlo проверяет частоту ложных отклонений H0 и эмпирическую мощность.
- Формирует Markdown/JSON-отчёт и график эффекта.

## Сценарий демонстрации

Метрика: доля уникальных пользователей, совершивших конверсию в одинаковом 7-дневном окне. Один пользователь — одно наблюдение. Условный baseline — 10%, вариант B — 12%.

| Параметр | Значение |
|---|---|
| H0 | pB − pA = 0 |
| H1 | pB − pA ≠ 0 |
| Уровень значимости | 0,05 |
| Плановая мощность | 0,80 |
| MDE | +2 процентных пункта, или +20% относительно 10% |
| Практический порог | +1 процентный пункт |
| Распределение | 50:50 |
| Финальный анализ | Один, после запланированного набора и созревания конверсий |

Baseline и MDE выбраны как учебные допущения. В реальной задаче baseline оценивается по истории, MDE и бизнес-порог обсуждаются до начала теста.

**MDE и практический порог различаются.** MDE — эффект, для которого рассчитывается заданная мощность. Практический порог — минимальная величина, имеющая ценность для задачи. Наблюдаемый эффект может быть меньше MDE и при этом статистически значимым.

## Команды по этапам

### План

```bash
python -m abtest plan --baseline 0.10 --mde 0.02 --alpha 0.05 --power 0.80 --daily-users 1000 --practical-threshold 0.01 --out local/plan.json
```

0.02 — именно 2 процентных пункта, не 2% относительного роста. План содержит минимальный размер групп, допущения и ориентировочную длительность набора. Расчёт мощности — нормальная аппроксимация, не точная гарантия. Для редких исходов и малых выборок нужен отдельный точный расчёт мощности.

Округление срока до полных недель — рекомендация для реального дизайна, а не реализованный календарный стоп. Демо симулирует ровно минимальную выборку и не моделирует дни недели. При выборе фиксированной календарной длительности нужно заранее зафиксировать её и ожидаемый объём; выборка может превысить минимум. Проверка planned_sample_reached проверяет только численность, а не соблюдение календарного дизайна и созревание конверсий.

### Симуляция

```bash
python -m abtest simulate --plan local/plan.json --p-a 0.10 --p-b 0.12 --seed 42 --out local/experiment.csv
```

Группы имеют точно одинаковый размер, порядок строк перемешан. Это упрощённая симуляция без сезонности и кластеризации. Истинные вероятности и seed сохраняются в соседнем .meta.json.

### Анализ

```bash
python -m abtest analyze --input local/experiment.csv --plan local/plan.json --out local/analysis
```

Для собственного CSV используется та же команда. Порядок колонок:

```csv
user_id,group,converted
user-001,A,0
user-002,B,1
user-003,A,1
user-004,B,0
```

user_id — уникальный идентификатор пользователя; group — A/B; converted — строго 0 или 1. Дубли пользователей, неизвестные группы, неверные исходы и пустые группы отклоняются. Программа не исключает неудобные наблюдения автоматически.

При отдельном analyze отчёт честно помечается как анализ входного CSV, без автоматического подтверждения происхождения данных. Демо явно помечено как симуляция. Для проверки созревания окна конверсии, корректности логирования, отсутствия пересечений и независимости пользователей нужен контроль процесса сбора — CSV не доказывает эти свойства.

Все выходные пути должны быть новыми: существующие файлы/папки не перезаписываются.

## Как читать результаты

- difference_percentage_points — абсолютная разница в процентных пунктах.
- relative_uplift — относительная разница в долях; 0.20 означает +20%. При нулевой конверсии A возвращается null.
- p_value — p-value двустороннего теста, не вероятность истинности нулевой гипотезы.
- confidence_interval_difference — доверительный интервал разницы в долях; умножьте на 100 для процентных пунктов.
- practical_threshold_confirmed — статистический критерий выполнен и нижняя граница CI не меньше бизнес-порога. Для итогового решения дополнительно учитываются SRM и полнота выборки.
- srm_flag — подозрительный дисбаланс численности A/B при пороге 0,001; это диагностика, а не подтверждение корректной рандомизации.
- planned_sample_reached — проверка численности относительно плана.
- decision — интерпретация с учётом указанных ограничений.

Если p-value ≥ α, результат называется неубедительным: равенство групп не доказано. Если p-value < α, это ещё не гарантирует достаточный бизнес-эффект. CI Newcombe и z-test/Fisher используют разные построения; около границы их выводы могут немного различаться.

Построение доверительного интервала не превращает p-value в оценку бизнес-ценности. Рекомендации проекта относятся только к выбранной основной метрике, без проверки защитных метрик.

## Monte Carlo

Команда demo выполняет по 1000 повторений при:

- pA = pB = 0.10: проверка частоты ложных отклонений H0;
- pA = 0.10, pB = 0.12: эмпирическая мощность при запланированном эффекте.

Частоты и стандартная ошибка симуляции сохраняются в demo/analysis/monte_carlo.json. Это не «post-hoc power» одного наблюдённого теста. Нормальная аппроксимация планирования и фактический метод тестирования могут давать немного разные значения мощности.

## Ограничения

Реализованы две независимые группы, бинарная метрика и один финальный анализ. Нет последовательных тестов, поправок на множество метрик и сегментов, CUPED, анализа выручки, кластерной рандомизации и обработки пропусков. Нельзя повторять анализ каждый день и останавливать тест при первом p < 0,05. Нельзя выбирать seed с красивым результатом и выдавать симуляцию за реальный рост продукта.
